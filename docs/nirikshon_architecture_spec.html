01 Executive Summary

Plain-language description of what this system actually is, for anyone touching backend, frontend, or LLM work.

Nirikshon screens chest X-rays for signs suspicious of pulmonary tuberculosis. It does this with two neural networks trained together, but only one of them ever sees a real patient's image after training is done.

A large network (ResNet-50, ~23.6M parameters) is trained first, as a "teacher." It never ships — its only job is to transfer what it learned to a second, smaller network (DenseNet-121, ~7.0M parameters), the "student," via a technique called knowledge distillation. The student is the only model that is ever exported, deployed, or shown a real uploaded image. This two-model setup exists because the student is what has to run affordably, on ordinary CPU hardware, for every screening request — the teacher's only value is making that smaller model better than it would be trained alone.

Before either network sees an image, a third, entirely separate network — an Attention U-Net — finds the lungs in the X-ray and everything outside that region is cropped away. This exists to stop the classifier from learning shortcuts (scanner labels, hospital markings, borders) instead of lung pathology.

The student's prediction is a probability that the image shows tuberculosis. That probability is compared against a threshold chosen mathematically from validation data (not a default 0.5) to produce a binary screening flag. Four different heatmap techniques (Grad-CAM, Grad-CAM++, LayerCAM, EigenCAM) can show which part of the image drove that decision.

The model is exported to ONNX format specifically so the serving environment doesn't need to run the same version of TensorFlow/Keras the model was trained with — this was a deliberate fix for a real Kaggle/training-environment version mismatch encountered during development.

Scope of this document

Everything in Sections 1–6 is Confirmed — read directly from the current state of nirikNetMain.py. Sections 7–9 (backend, frontend, LLM) mostly describe a Derived contract inferred from the model's actual inputs/outputs, since none of that layer is implemented yet. A few points there are Decided — a real project decision has been made, just not yet built (e.g. the LLM provider). Where something genuinely isn't resolved, it's marked Not defined rather than guessed.

02 End-to-End AI Pipeline

Every stage from upload to display, and why each one exists. Not defined stages are training-pipeline concepts with no built inference-serving equivalent yet.

Correcting a term in the requested outline

The outline for this document lists Attention Module as a stage between Segmentation and the Student Model. That stage does not exist as a separate step. Attention exists only as attention gates inside the Attention U-Net's decoder (Section 3) — it is part of how segmentation works, not a second processing stage after it. Stating this explicitly rather than inventing a module that isn't in the code.

Why DenseNet-121 was selected

  • Pretrained initialization. The architecture it replaced (a bespoke CNN, "NirikNet") trained from random weights — a real overfitting risk given the training pool's size. DenseNet-121 starts from ImageNet weights.
  • Narrower teacher/student capacity gap. 23.6M → 7.04M is a ~3.35× gap, down from ~11× with the previous student — addressing degraded distillation quality under large capacity gaps (Mirzadeh et al., 2020).
  • Domain precedent. DenseNet-121 is the architecture CheXNet (Rajpurkar et al., 2017) established for chest-radiograph classification specifically.
  • Accepted trade-off. CPU inference is slower than the model it replaced — ~750–870ms/image measured on Kaggle's CPU-forced benchmark, versus ~260–490ms for the previous student. Judged acceptable because this is a non-real-time, single-image screening upload, not a live feed.

Role of ResNet-50

Training-time only. Supplies temperature-scaled soft targets to the distillation loss. Never receives a real patient image outside training; never exported.

Knowledge Distillation workflow

Implemented in DistillationModel. Both networks end in a softmax layer for standalone use (evaluation, Grad-CAM), but distillation math is computed on the pre-softmax logits via a "logits submodel" view into each network's graph — a fix for a softmax-of-softmax bug found earlier in this project (re-softmaxing an already-softmaxed output flattens gradients and corrupts both loss terms).

Soft teacher targetssoftmax(teacher_logits / T)
Soft student outputsoftmax(student_logits / T)
Distillation lossKLD(soft_teacher, soft_student) × T²
Hard-label lossFocalCE(y, softmax(student_logits)), T=1
Total lossα × hard_loss + (1−α) × distill_loss
T (temperature)3.0
α (hard-loss weight)0.5

Both teacher and student train in two stages each (frozen head warmup → partial backbone unfreeze). The student's two stages both run inside a fresh DistillationModel wrapping the (already fully-trained, frozen) teacher.

Attention mechanism

Exists only inside the segmentation U-Net, as soft attention gates (_attention_gate()) at each decoder level: 1×1 convs on the encoder skip-connection and the up-sampled decoder signal, added, ReLU'd, projected to a single channel, sigmoid'd, then multiplied elementwise against the skip connection. Neither ResNet-50 nor DenseNet-121 contains any attention mechanism — no SE blocks, no CBAM, no self-attention. Stating this plainly since it's easy to assume otherwise from the pipeline outline.

Lung segmentation

Attention U-Net, 4-level encoder/decoder, base_filters=32 doubling per level (32 → 64 → 128 → 256, bottleneck 512). Input 256×256×1 grayscale, output 256×256×1 sigmoid mask. At inference, binarized at >0.5, largest-2-connected-components kept, then morphologically opened+closed (5×5 kernel) before the bounding box is computed.

Feature extraction

Standard ImageNet-hierarchy convolutional features from each backbone. Final feature map before pooling: ResNet-50 → 7×7×2048; DenseNet-121 → 7×7×1024.

Classification head

Identical shape for both networks: GlobalAveragePooling2D → BatchNormalization → Dropout → Dense(2, linear) → Activation(softmax). Only the dropout rate differs (teacher 0.2, student 0.3).

Output layer

Dense(2) raw logits, immediately followed by Activation("softmax") as a separate layer (not baked into the Dense activation) — this split exists specifically so the distillation math can read pre-softmax logits without disturbing the model's normal softmax-output behavior.

All six classification sources are pooled into one dataframe, deduplicated, quality-filtered, rebalanced to a 2:1 Normal:TB ratio, then split patient-wise 70/15/15.

Preprocessing

Single shared function, preprocess_xray() — see Section 2, Stage 2. Identical for every source, every split, and (architecturally required) inference.

Augmentation — train split only

  • RandomRotation ±10°, RandomTranslation ±7%, RandomZoom ±8%
  • Random brightness (δ=15), random contrast (0.85–1.15), additive Gaussian noise (σ=6)
  • No horizontal flip — CXR laterality (which lung a finding is in) is diagnostically meaningful

Loss functions

CategoricalFocalCrossentropy (γ=2.0, α=0.25) for every hard-label term — teacher training and the student's hard-label component inside distillation alike. KL-divergence (temperature-scaled) for the soft-target distillation term.

Optimizer & scheduler

AdamW throughout, weight decay 1e-4. Custom warmup + cosine-decay schedule, per stage:

StagePeak LRWarmup epochsTotal epochs
Teacher head (frozen)1e-3515
Teacher finetune (conv4/conv5 unfrozen)1e-4540
Student head (frozen)1e-31010
Student finetune (conv5_block* unfrozen)1e-410100

Metrics

Accuracy, precision, recall/sensitivity, F1, ROC-AUC, PR-AUC, specificity, balanced accuracy, MCC, Cohen's kappa, full confusion matrix and classification report — computed for teacher and student, on both validation and test splits.

Validation & threshold selection

Patient-wise 70/15/15 split via GroupShuffleSplit on patient_id. Validation drives early stopping, checkpointing, and the operating threshold (Youden's J statistic, maximizing sensitivity + specificity − 1) — that threshold is then frozen and applied once to the test split, never refit on it.

Checkpointing

Each of the four training stages saves and reloads its own best-epoch weights independently (monitor: val_accuracy, mode max), with restore_best_weights=True plus an explicit reload as a second safeguard. Early-stopping patience: 15 (classification stages), 6 (segmentation).

05 Inference Architecture

What must actually be loaded and run to score one uploaded image.

Deployment platform Decided

Backend + model on Hugging Face Spaces. Frontend on Vercel. This isn't a new constraint introduced by that choice — it's confirmation of an assumption the training code already had baked in. benchmark_inference_latency()'s own docstring reads: "forced onto CPU regardless of GPU availability, since the deployment target (HF Spaces free tier) is CPU-only" — and the ONNX export stage's docstring cites the same reasoning for exporting rather than serving native Keras. The ~750–870ms/image DenseNet-121 CPU figure in Section 3 was always measured with exactly this environment in mind, not a generic benchmark.

Models loaded

  • DenseNet-121 student — Confirmed, exported to ONNX (opset 13). The only classifier deployed.
  • Attention U-Net — Confirmed required, because segmentation runs on every image, training or inference, as part of preprocess_xray(). Its export format is Not defined: the code saves it as a native .keras file (model.save()) — there is no ONNX export path for it anywhere in nirikNetMain.py. Whether the serving stack should add one, to match the student's ONNX-only design, was never decided.

Models NOT loaded

  • ResNet-50 teacher — training-only by design. Loading it in a serving environment would be a deviation from this architecture, not a variant of it.
Open architectural gap — explainability vs. ONNX

Grad-CAM/Grad-CAM++/LayerCAM/EigenCAM (compute_gradcam etc.) require a TensorFlow GradientTape over the live Keras model's intermediate layers. ONNX Runtime does not support this. If only the ONNX student is loaded in production, explainability as currently implemented cannot run against it. This was never resolved in this project. Two real options, neither decided: (a) keep the native Keras student loaded alongside the ONNX one, used only for explainability; (b) implement an ONNX-compatible CAM method separately. Marking this Not defined rather than picking one.

Image preprocessing

Must exactly replicate preprocess_xray() — CLAHE (2.0 / 8×8), 8.5%-padded lung-mask crop, resize to 224×224, canonical 0–255 RGB. Model-specific normalization is not a separate serving-side step — it's baked into the exported graph via each model's own Lambda layer.

Output generation

Softmax pair → apply the frozen Youden threshold from metrics.json (training-time artifact) to P(Tuberculosis) → binary screening flag. The threshold must never be recomputed at inference time.

06 Explainability Architecture

MethodMechanismNeeds class index?
Grad-CAMGradient-weighted class activation mapping (Selvaraju et al.)Yes
Grad-CAM++Refined per-pixel weighting (squared/cubed gradient terms) for better multi-region localizationYes
LayerCAMElementwise ReLU'd gradient weighting (finer-grained than Grad-CAM's global pooling)Yes
EigenCAMGradient-free — principal component of the conv feature map's covariance, projected per pixelNo

All four operate on the student's DenseNet-121 backbone, target layer auto-detected by type (the nested backbone submodel), not by a hardcoded layer name.

Named but not implemented

The project's broader documentation describes a "Consensus CAM" (an average of the four normalized CAM outputs) as part of the canonical explainability stage. No such computation exists in nirikNetMain.py — only the four individual CAM variants are generated and saved separately. This is a real gap between documented intent and implementation, not a naming difference.

Attention maps as an explainability output

Not defined. As established in Section 3, attention only exists inside the segmentation U-Net's decoder gates. No code exposes those gate activations as a classification-explainability artifact — the segmentation mask itself is a real, available output, but it's a lung-localization boundary, not an attention heatmap over the classifier's decision.

Confidence & feature importance

Confidence: raw P(Tuberculosis) softmax value (Section 2, Stage 6). Feature importance beyond the CAM family: Not defined — no SHAP, LIME, or permutation-importance code exists.

How this should be exposed to the backend

Derived — no serialization or API code exists for this. Each compute_* function returns a single-channel array normalized to [0, 1] at the input resolution; a reasonable backend contract is to overlay each onto the preprocessed (post-crop, post-CLAHE) image server-side and return either encoded images or the raw arrays, per endpoint design in Section 7.

07 Backend Requirements

Every item here is Derived — a contract inferred from the model's actual I/O, not existing backend code. This project has a backend/ directory already, but it was out of scope this session and has not been reconciled against this architecture (old model references, stale thresholds — see the closing note).

Deployment target Decided

Hugging Face Spaces — both the backend API and the model artifacts. An hf_space/ directory with a working Dockerfile already exists in this repository (FROM python:3.11-slim, EXPOSE 7860 — the standard Hugging Face Spaces Docker-SDK port), so the container convention is already scaffolded; it hasn't been reconciled against the DenseNet-121/ONNX/Youden-threshold architecture described in this document. Concretely: the free tier's CPU-only constraint (Section 5) is the real reason the student was exported to ONNX at all rather than served as native Keras.

The threshold_used value must be read from the training run's metrics.json (student_youden_threshold), never hardcoded to 0.5 and never recomputed server-side.

Model loading strategy

Load the student (ONNX Runtime session) and the U-Net (native Keras) once, at process startup — not per-request. The teacher must never be loaded in a serving process.

Preprocessing / postprocessing requirements

Preprocessing must exactly match preprocess_xray() (Section 2/5) — this is a hard requirement, not a suggestion. Postprocessing: apply the frozen threshold; do not apply any additional calibration not present in the training pipeline.

Error handling (derived from the code's own failure surface)

  • Unreadable/corrupted image → read_image_grayscale() raises ValueError — map to a 4xx.
  • No lung region detected → the current code silently falls back to the full, uncropped image (bounding_box_with_padding's empty-mask branch) rather than erroring. This is existing behavior, not a recommendation — worth flagging to a clinician-facing UI as a quality caveat rather than treating it as an error.

08 Frontend Requirements

Derived display contract — no frontend code was in scope. Deployment target is Decided: Vercel. It calls the backend on Hugging Face Spaces (Section 7) as a remote API — it never loads any model itself.

  • Upload: single image, formats matching what read_image_grayscale() accepts.
  • Prediction: must use the project's mandated clinical language — "AI Screening Result — Suspicious for Pulmonary Tuberculosis" or "Normal". Never "Confirmed," never "Diagnosed."
  • Confidence: show P(Tuberculosis) alongside the operating threshold it was compared against — Youden-derived thresholds observed in real runs were far from 0.5 (e.g. 0.079–0.124), so showing the raw probability without its threshold would read as confusing or arbitrary to a clinician.
  • Heatmap: whichever CAM variant(s) the backend returns, overlaid on the cropped/preprocessed image.
  • Attention visualization: Not defined as a classification artifact (Section 6). If the lung segmentation mask itself is shown, label it as segmentation/localization, not "attention."
  • Explainability: the four individual CAM outputs. A "Consensus CAM" cannot be shown until it exists in the model pipeline (Section 6).
  • Chat: Not defined — depends entirely on Section 9, which is itself unbuilt.
  • Loading state: functionally necessary, not optional polish. Measured student latency alone is ~750–870ms/image on CPU; add U-Net segmentation plus up to four gradient-tape CAM passes, and a real end-to-end request is a multi-second operation.
  • Error states: Not defined beyond what Section 7's error-handling notes imply.

09 LLM Integration

The provider is Decided — a real project decision, not yet implemented. Everything else below is still Derived: a design recommendation inferred from the project's stated intent, not existing behavior.

Provider Decided

Gemini 2.5 Flash, called via a Google AI Studio API key. No integration code exists yet — this section describes how that call should be shaped once it's built, not something already running.

Handling the API key

Server-side only, read from an environment variable / secrets manager — never bundled into the frontend, never logged alongside request/response payloads. This is a general requirement for any cloud LLM key, worth stating plainly since it's the most common way this kind of integration leaks credentials.

Where it fits

After classification and explainability are complete, before final display — it narrates already-computed results, it does not produce them.

What it should receive

Only structured, already-computed outputs: prediction label, confidence, threshold, and (if later implemented) a CAM-derived localization summary. Anatomical zone mapping (e.g. "right upper lobe") is described in the project's broader documentation but has no implementation in nirikNetMain.py — do not assume it's available as an LLM input until it exists.

What it should NEVER receive

  • The raw uploaded image, unless and until image-grounded generation is specifically validated for this task — passing it "for context" invites the model to freelance a visual read it has no validated grounding for.
  • Model weights, training data, or any patient-identifying information beyond what a report strictly requires.
  • Any instruction that could produce diagnostic-sounding language — the project's own clinical safety rules forbid "confirmed," "diagnosed," or similar framing.

Hallucination minimization

Constrain the prompt to only comment on the numeric fields it's given; do not ask it to independently interpret the image. Enforce the clinical terminology rules (Section 8) at the system-prompt level, not just by convention.

Follow-up questions

Not defined.
